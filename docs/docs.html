V1.0.0-PREVIEW.1

Start with one connection.

Tunlite is a single Go binary that turns native OpenSSH forwards into named, OS-managed connections. The preview supports macOS and Linux; Windows is not published yet.

01 · INSTALL

Install the native binary

The only runtime dependency is the system ssh. The bootstrap downloads the platform archive and verifies its SHA-256 before installation.

$ command -v ssh
$ curl -fsSL https://raw.githubusercontent.com/yuanyuanzijin/tunlite/master/bootstrap.sh | sh
$ ~/.local/bin/tunlite version --json
Release not published yet? A 404 is expected before the Preview Release exists. Testers can install a supplied native binary with install -m 0755 ./tunlite ~/.local/bin/tunlite.

02 · DECLARE

Create your first connection

Use the same forward syntax as OpenSSH. Forward flags are repeatable, and add creates a stopped native service—it does not open a connection.

# local TCP forward
$ tunlite add db --to deploy@app01 -L 5432:localhost:5432

# remote publish and SOCKS proxy
$ tunlite add preview --to deploy@app01 -R 9000:localhost:3000
$ tunlite add socks --to deploy@app01 -D 1080

Identity files, jump hosts, groups, and safe OpenSSH Key=Value options are explicit fields:

$ tunlite add private-db --to deploy@app01:2222 \
    -i ~/.ssh/work_ed25519 --jump bastion@example.com \
    -L 5432:localhost:5432 --group work

03 · RUN

Choose who owns the lifecycle

CommandModeOwnership
tunlite run dbforegroundCurrent terminal; Ctrl-C stops it
tunlite start dbbackgroundNative service for this login session
tunlite enable dbpersistentNative service now and on future logins
$ tunlite check db --timeout 12
$ tunlite start db
$ tunlite status db
$ tunlite logs db --lines 100
$ tunlite stop db
Use system OpenSSH tools to manage keys. Tunlite never generates credentials, copies public keys, weakens host-key checking, or modifies remote authorized_keys.

04 · OBSERVE

State without guesswork

Status separates five questions that older tunnel tools often collapse into one word:

serviceStateIs a native definition registered?
modeStopped, foreground, background, or persistent?
processStateIs the provider process actually running?
healthDo configured endpoint probes pass?
consistencyStateDoes the system definition match Tunlite?
$ tunlite doctor db --offline
$ tunlite resolve db --use tunlite --dry-run
$ tunlite resolve db --use system

Drift repair always names the source of truth. There is no silent overwrite of a native service definition.

05 · AUTOMATE

A versioned interface for agents

Use --json --non-interactive and verify protocolVersion before mutation. Use --dry-run whenever the command supports it.

$ tunlite capabilities --json --non-interactive
$ tunlite schema cli --json --non-interactive
$ tunlite add db --to deploy@app01 -L 5432:localhost:5432 \
    --dry-run --json --non-interactive

Batch operations return one result per connection. Exit code 5 means partial failure; inspect every item instead of treating it as total failure or success.

06 · MIGRATE

Move from 0.10.3 side by side

Keep the old tunlite command and V1 binary separate. Import is one-way and read-only with respect to 0.x: it never edits the source file, stops the old daemon, or starts V1 connections.

$ ./tunlite-v1 import ~/.config/tunlite/config.json \
    --dry-run --json --non-interactive
$ ./tunlite-v1 import ~/.config/tunlite/config.json

# switch one connection only after inspecting it
$ tunlite disable db
$ ./tunlite-v1 start db
Never run both versions of the same connection. Local ports conflict, and duplicate remote forwards can be ambiguous. Keep the old config until every connection has passed real traffic and login-recovery tests.
